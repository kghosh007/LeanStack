LeanStack Production Operations Manual

The authoritative reference for deploying, operating, caching, sandboxing, and upgrading high-density WordPress infrastructure with lsctl.

1. Architecture Overview & Ground-Up Thinking

LeanStack discards legacy control panel paradigms. Instead of running persistent, memory-heavy background daemons in Java, Node.js, or Ruby that consume 1.5GB to 3GB of RAM before hosting a single website, LeanStack is built as an event-driven, decoupled control engine.

The control plane (lsctl) operates with an idle footprint of less than 15 MB RAM using SQLite in WAL mode. This guarantees that virtually 100% of your host's physical RAM is reserved for what actually drives your business: MariaDB buffer pools, Valkey object caching, and high-concurrency PHP workers.

Why Sub-15MB RAM Changes Everything: On a 4GB VPS, conventional panels steal up to 40% of the server's memory for their own administrative web GUI. Under LeanStack, that entire 4GB belongs to your WordPress workloads, easily tripling your concurrent tenant density without degrading Time-to-First-Byte (TTFB).

2. Installation & Self-Hosting Guide

2.1 Server Prerequisites

LeanStack is strictly verified for modern production cloud VPS and dedicated servers satisfying:

  • Operating System: Clean, minimal installation of Ubuntu 22.04 LTS, Ubuntu 24.04 LTS, or Ubuntu 26.04 LTS (x86_64 architecture).
  • CPU: 1 vCPU minimum (2+ vCPUs strongly recommended for production multi-tenant environments).
  • RAM: 1 GB minimum (2+ GB recommended for WooCommerce or high-traffic sites).
  • Network Ports: Port 22 (SSH), Port 80 (HTTP), and Port 443 (both TCP and UDP for HTTP/3 QUIC) must be open in your cloud provider's firewall.

2.2 Method A: 1-Line Hosted Bootstrap (Recommended)

On your fresh Ubuntu server, run the official zero-friction bootstrap installer:

curl -fsSL https://leanstack.kuntalghosh.dev/install.sh | sudo bash

2.3 Method B: Self-Hosting & Fleet Automation

LeanStack is designed from the ground up for agencies, cloud engineers, and hosting providers who require full sovereignty over their infrastructure. You can self-host LeanStack across your private cluster using non-interactive deployment flags:

sudo /opt/leanstack/install.sh --non-interactive --profile=agency_woocommerce --php=8.5
Public GitHub Repository: The official public GitHub repository for LeanStack is scheduled for public release in Q4 2026. During this phase, enterprise installations are bootstrapped directly via the signed curl installer above.

2.4 Cloud-Init & Ansible Automation

To provision LeanStack automatically upon VPS creation in Hetzner, AWS, DigitalOcean, or Vultr, add this snippet to your Cloud-Init user data:

#cloud-config
runcmd:
  - curl -fsSL https://leanstack.kuntalghosh.dev/install.sh -o /tmp/install.sh
  - chmod +x /tmp/install.sh
  - /tmp/install.sh --non-interactive --profile=default --php=8.5

3. Master CLI Reference (lsctl)

The master command-line tool is installed at /usr/local/bin/lsctl (LeanStack Control). It manages tenant lifecycles, runtime switching, diagnostics, and background task queues.

Backwards Compatibility: If you have scripts or muscle memory using cpctl, LeanStack provides a transparent alias wrapper at /usr/local/bin/cpctl pointing directly to lsctl.

3.1 Provisioning a WordPress Site

Creates an isolated POSIX user, dedicated PHP-FPM socket pool, MariaDB database, Valkey ACL credentials, Let's Encrypt SSL certificate, and compiled Angie virtual host:

sudo lsctl site:create --domain=shop.example.com --profile=agency_woocommerce --php=8.5 --cf

Note: sudo lsctl wp:create is also accepted as a synonym.

3.2 Zero-Downtime PHP Runtime Switching

Instantly transition a live site to any installed PHP runtime (e.g. 8.3, 8.4, or 8.5) with zero dropped connections:

sudo lsctl site:php shop.example.com 8.5

3.3 Site Inventory & JSON Inspection

View all provisioned tenants or inspect a single tenant's metadata formatted for terminal or automation pipes:

sudo lsctl site:list --json sudo lsctl site:info shop.example.com --json

3.4 Deep Site Teardown (Zero Leftover Orphans)

Safely destroys a site while creating an atomic SQL safety snapshot in /var/backups/lsctl/trash/. It removes all virtual hosts, SSL certificates, PHP-FPM pools, MariaDB database and user, Valkey keys, and Linux accounts:

sudo lsctl site:delete shop.example.com

3.5 System Health Doctor

Audits Angie, MariaDB, Valkey, system sockets, open files, and storage metrics:

sudo lsctl doctor

3.6 Reconcile Tenant Sites

Synchronizes Must-Use plugins and Angie configuration templates across all registered tenants:

sudo lsctl sync-tenants

4. Operational Agency Profiles

LeanStack agency profiles are configured in /etc/lsctl/profiles.yaml (with fallback support for /etc/cpctl/profiles.yaml). They allow operators to apply tailored PHP memory limits, caching heuristics, and worker bounds with a single flag:

5. Caching & SSI Invalidation Suite

5.1 Dedicated Per-Tenant FastCGI Microcache

Each domain is given an isolated cache storage directory in /var/cache/angie/sites/${DOMAIN}/ and a dedicated Angie zone CACHE_<domain>.

  • Zero Noisy-Neighbor Cache Flushing: Purging site A has zero impact on the cache hit ratio of site B.
  • Surgical Single-URL Invalidation: When a post or page is published, updated, or trashed, LeanStack's Must-Use plugin calculates the MD5 hash of the URL and deletes only that specific cache file via levels=1:2 directory unlinking.
  • In-Dashboard Controls: Inside WordPress Admin, navigate to Tools > LeanStack Cache to toggle caching on/off, change TTL, flush the entire site cache, or invalidate a specific URL.

5.2 Universal SSI Hole-Punching

Dynamic personalized elements are rendered into cached HTML shells using Angie's native ssi on; engine: 

<!-- Dynamic Cart Count Hole-Punched at Wire Speed -->
<!--# include virtual="/leanstack-esi/?action=cart_count" -->

<!-- Nonce Injection (Prevents Expired Form Nonces on Cached Pages) -->
<!--# include virtual="/leanstack-esi/?action=nonce" -->

<!-- Batched Carousel Prices (1 Subrequest for Multiple Product Cards) -->
<!--# include virtual="/leanstack-esi/?action=batch_price&ids=10,20,30" -->
Visual Page Builder Immunity: SSI tags are automatically disabled whenever a page builder editor session is active (e.g. ?bricks=run, ?elementor-preview=, ?et_fb=), ensuring visual canvases are never corrupted.

5.3 Non-Conflicting APCu Application Cache

LeanStack deploys APCu memory caching via wp-content/mu-plugins/leanstack-apcu.php rather than dropping an object-cache.php file. This preserves 100% compatibility with Valkey/Redis Object Cache Pro plugins without collisions. Keys are cryptographically isolated per tenant using ls_<md5>: prefixes.

5.4 Cloudflare Edge CDN Integration

Configure your Cloudflare Zone ID and API Token under Tools > LeanStack Cache > Cloudflare Edge CDN. Single post updates trigger dual invalidation: clearing local FastCGI microcache files and Cloudflare Edge caches simultaneously.

6. Tenant POSIX Sandboxing & Inotify Gatekeeper

LeanStack provides dedicated, safe configuration slots per tenant under /home/<user>/nginx/:

  • custom-early.conf: Evaluated before static asset caching. Ideal for image processors (CompressX WebP/AVIF rewrites).
  • custom-rules.conf: Evaluated before the WordPress router. Ideal for custom redirects and proxy rules.
  • security-headers.conf: HTTP security headers (CSP, HSTS, X-Frame-Options).
Inotify Gatekeeper (ls-gatekeeper): Whenever a file in /home/*/nginx/ is modified, ls-gatekeeper intercepts the write and runs ls-nginx-linter. If any syntax error exists, the reload is blocked and logged, preventing broken configs from taking down Angie.
WebAssembly Media (Wasm-vips) CSP Requirement: If defining a Content Security Policy, ensure worker-src 'self' blob:; is enabled to support client-side image processing in modern WordPress.

7. In-House Anti-Thundering Cron Queue (ls-cron-queue)

WordPress's default cron architecture executes scheduled maintenance jobs whenever a random visitor loads a page. During viral traffic spikes, this leads to catastrophic lock storms: dozens of visitor requests simultaneously trigger the same background cron job, locking database tables and adding hundreds of milliseconds of latency to page load times.

7.1 The LeanStack Cron Architecture

LeanStack eliminates this behavior at the root:

  1. Global Visitor Cron Lockout: In every tenant's wp-config.php, LeanStack inserts define('DISABLE_WP_CRON', true);, guaranteeing that visitor requests never invoke wp-cron.php.
  2. Serialized Systemd Dispatcher: Native Linux systemd timer /etc/systemd/system/ls-cron.timer triggers every 60 seconds with strict 1s accuracy.
  3. Atomic Flock Mutex: ls-cron-queue acquires an exclusive file lock (/var/lock/ls-cron.lock), ensuring that previous long-running cron batches never overlap with new runs.
  4. Isolated WP-CLI Execution: Each tenant's due events are executed as that tenant's POSIX user with strict memory boundaries: sudo -u wp_example wp cron event run --due-now.

7.2 Cron Queue Commands

# Run all due crons across all registered tenants: sudo ls-cron-queue --all # Run crons for a specific tenant: sudo ls-cron-queue --domain=shop.example.com # Inspect cron execution log: tail -f /var/log/lsctl/cron.log
Systemd Service / Timer Frequency Function
ls-cron.timer Every 60s Dispatches serialized WP-CLI cron queues across all sites, eliminating visitor wait latency.
ls-cf-sync.timer Daily (03:00) Fetches current Cloudflare IPv4 & IPv6 CIDRs and updates Angie real-ip directives.
ls-gatekeeper.service Continuous Inotify Validates tenant custom Nginx rules using ls-nginx-linter before reloading Angie.

8. Autonomous Fleet Upgrades

Upgrade your LeanStack installation across single servers or multi-server fleets with automated rollback protection:

# 1-Line Remote Upgrade: curl -fsSL https://leanstack.kuntalghosh.dev/update.sh | sudo bash # Or directly via lsctl CLI: sudo lsctl update # Simulate upgrade without making any system changes: sudo lsctl update --dry-run

The Transactional Upgrade Pipeline automatically:

  1. Executes pre-flight syntax checks on Angie configuration (angie -t).
  2. Creates an atomic snapshot of /var/lib/lsctl/sites.db in /var/backups/lsctl/.
  3. Pulls the latest git release via git pull --ff-only.
  4. Applies incremental forward schema migrations inside SQLite transactions.
  5. Synchronizes Must-Use plugins across all registered tenant sites.
  6. Validates syntax again and performs zero-downtime Angie reload. On any failure, automatically rolls back to snapshot.

9. Backups & Disaster Recovery

LeanStack stores all site metadata, database credentials, and operational settings in SQLite at /var/lib/lsctl/sites.db (with fallback resolution for /var/lib/cpctl/sites.db).

# Backup control plane database: sqlite3 /var/lib/lsctl/sites.db ".backup '/var/backups/lsctl/manual_backup_$(date +%F).db'" # Export single WordPress database: cd /home/<user>/htdocs && sudo -u <user> wp db export /home/<user>/backup.sql

10. Emergency Diagnostics & Health Doctor

Essential diagnostic commands when inspecting host behavior:

# 1. Comprehensive LeanStack health audit
sudo lsctl doctor

# 2. Test Angie configuration syntax
angie -t

# 3. Reconcile all tenant Must-Use plugins
sudo lsctl sync-tenants

# 4. View CrowdSec firewall decisions & unblock an IP
cscli decisions list
cscli decisions delete --ip <your-ip>

# 5. View Gatekeeper daemon real-time logs
journalctl -u ls-gatekeeper -f
